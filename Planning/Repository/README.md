# Repository structure

> **Living document:** All material in `Planning/` is generated by AI through discussions and direction from the developer; it is not written by hand. It provides structure, guidance, and context for ongoing development, and will be reviewed and updated periodically as Stagehand evolves.

This folder describes the shape of the Stagehand repository. The companion [structure](structure.md) document records the proposed monorepo footprint. The root npm workspace and initial CLI, web editor, and reusable-package folders exist. Plan-schema validates plans/cases, selects named data sets, and expands/prepares one-level shared steps with caller/inner-step identity. Runner-core dispatches those prepared shared steps through `executeCase` and keeps that identity on preparation, hard-step, and soft-assertion failures. Its browser-free `prepareRunForExecution` helper can prepare caller-supplied cases before startup, but full orchestration has not yet connected that preparation to browser lifecycle, and result generation remains unimplemented. Plan-engine loads a plan and its referenced cases from disk, checks filesystem containment, validates the loaded bundle, and calculates its source fingerprint. Result-model has the normative result v1 JSON Schema, TypeScript types, runtime validation, and an example. Runner-core starts Chromium, creates isolated case sessions, resolves case locators, runs ordered waits, executes actions/assertions, and gathers accessibility observations. The earlier development-container runner-core command passed 137 mocked-browser tests; updated shared-step execution verification is pending. These mocked checks do not establish successful real-browser scans. Some workspaces remain scaffolds, and other directories in the footprint remain future targets. Real-browser accessibility verification remains outstanding.

## Current top-level folders

- [`Planning/`](../README.md) - product backlog, roadmap, security planning, and work plans.
- [`Learning Plan/`](../../Learning%20Plan/README.md) - learning materials that prepare for Phase 1 work.
- `apps/` - initial CLI and Vue editor npm workspace scaffolds; no app behaviour is implemented yet.
- `packages/` - reusable-package npm workspaces; plan-schema, plan-engine, result-model, and runner-core have implementation code. The remaining packages are scaffolds.
- [`Planning/Diagrams/`](../Diagrams/M1-component-dependency-graph.md) - editable diagrams that clarify proposed architecture and planning relationships.

## Application and package workspaces

These workspaces have `package.json` manifests. Plan-schema has JSON Schemas, a TypeScript public entry point, synchronous schema validators, a relative case-reference matcher, parsed-bundle validation, variable/data-set/shared-step preparation helpers, tests, and synthetic examples. Plan-engine has a TypeScript public entry point and Node-side plan/case file loader with filesystem containment checks, source fingerprint calculation, and tests. Result-model has a normative result v1 JSON Schema, TypeScript types, runtime validation, tests, and a synthetic example. Runner-core has a TypeScript public entry point for Chromium run/case-session lifecycle, locator resolution, ordered waits, actions, assertions, and prepared case/shared-step dispatch. Soft text, HTML, and input-value failures are returned to the caller; optional associated-label failures are always soft. Runner-core also resolves accessibility settings and exposes explicit scans plus automatic scan/collection. Its tests use browser and axe doubles; updated shared-step execution verification, real-browser testing, and result production remain future work. The remaining app and reporter workspaces remain scaffolds with notes about their planned source entries and checks:

- `apps/cli/` - command-line app workspace.
- `apps/web/` - Vue editor app workspace.
- `packages/` - reusable workspaces for runner core, plan schema, plan engine, result model, and provisionally reporters.

The root `package.json` declares the npm workspaces, and the root `package-lock.json` records their dependency tree. API and desktop apps remain later possibilities.

## Other proposed folders

These paths are described in `structure.md` but have not been created as part of the initial workspace scaffold:

- `examples/` - sample test plans that demonstrate how Stagehand plans are written and used.
- `docs/` - product and technical documentation for users and contributors.
- `website/` - the public project website, if the project needs one.
- `tests/` - broader tests that cover behaviour across packages or applications.
- `tools/` - repository maintenance and development utilities.

At the repository root, the proposal also calls for project guidance (`README.md`, `CONTRIBUTING.md`, `SECURITY.md`, and `AGENTS.md`) and shared TypeScript configuration. Those files describe or configure the repository as a whole rather than belonging to one application package.

Treat the proposed layout as a guide for decisions, not evidence that every component has been built. The `structure.md` file says so too; a tidy drawing still doesn't make the road appear.

## Runner-core source navigation

Runner-core now has feature modules beneath `src/`, with a small `index.ts` that explicitly re-exports the existing public API. Run setup/shutdown remains in `browser/run.ts`; session methods and findings/history live in `browser/case-session.ts`. Actions have separate interaction files; assertions, locators, waits, step dispatch, and accessibility each have their own modules. See the [package source map](../../packages/runner-core/README.md#source-structure) and [repository footprint](structure.md). This is an internal restructure, not a new package boundary or public subpath API.

## Plan-schema source navigation

Plan-schema also keeps a small `src/index.ts` as its single public entry point. Schema and semantic validation live under `src/validation/`, case-reference matching under `src/references/`, and ordinary variable resolution and case preparation under `src/variables/`; `src/json.ts` contains their small shared JSON helpers. Consumers continue importing from `@stagehand/plan-schema`, not from these internal modules. See the [package guide](../../packages/plan-schema/README.md) and [repository footprint](structure.md).
