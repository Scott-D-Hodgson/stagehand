# Repository structure

> **Living document:** All material in `Planning/` is generated by AI through discussions and direction from the developer; it is not written by hand. It provides structure, guidance, and context for ongoing development, and will be reviewed and updated periodically as Stagehand evolves.

This folder describes the shape of the Stagehand repository. The companion [structure](structure.md) document records the proposed monorepo footprint. The root npm workspace and initial CLI, web editor, and reusable-package folders exist. The plan-schema package contains shared plan/case validation, relative case-reference matching, parsed-bundle validation, and absolute HTTP/HTTPS navigation URL checks. The plan-engine package loads a plan and its referenced cases from disk, checks that resolved case files stay inside the plan folder, validates the loaded bundle, and calculates its source fingerprint. The result-model package contains the normative result v1 JSON Schema, TypeScript types, runtime validation, and a synthetic example. Runner-core starts Chromium, creates isolated case sessions, resolves case locators, and runs ordered waits. It supports navigation, click, typing, fill, option selection, and exact `assertText`/`assertHtml`/`assertValue` checks through both direct methods and validated step dispatch. Automatic after-step axe scanning, result generation, and full plan orchestration remain unimplemented. Runner-core also resolves validated accessibility settings through a pure helper and per-session snapshots, preserving independent overrides and copied tag arrays. Case sessions also expose explicit scanAccessibility calls using resolved enable/tag settings and returning raw axe observations or preserved execution errors. Before the mapping slice, the build and all 99 tests passed locally on Windows; these mocked checks do not establish successful real-browser scans. Tests mock Playwright; dev-container, real-browser, and current CI verification of the `assertValue` slice remain outstanding. Some workspaces still remain scaffolds, and other directories in the footprint remain future targets. A separate pure mapAccessibilityFindings helper projects raw violations into shared result-model types, preserving selected evidence and counting mapped nodes. A caller-owned `createAccessibilityFindingCollector` now accumulates mapped findings per case by exact URL/description and markup, retaining first-observed evidence and updating counts. The expanded 117-test runner-core suite passes locally on Windows. Automatic session/collector integration remains pending.

## Application and package workspaces

These workspaces have `package.json` manifests. The plan-schema package has JSON Schemas, a TypeScript public entry point, synchronous schema validators, a relative case-reference matcher, parsed-bundle validation, absolute HTTP/HTTPS navigation URL checks, package tests, and synthetic examples. The plan-engine package has a TypeScript public entry point and Node-side plan/case file loader with filesystem containment checks, source fingerprint calculation, and tests. The result-model package has a TypeScript public entry point, normative result v1 JSON Schema, runtime validation, tests, and a synthetic example. The runner-core package has a TypeScript public entry point for Chromium run/case-session lifecycle, locator resolution, ordered waits, and direct navigation/click/type/fill/selectOption methods. It also provides direct and dispatched `assertText`/`assertHtml`/`assertValue` checks for validated steps. Soft text, HTML, and input-value failures are returned to the caller; optional associated-label failures are always soft. Runner-core also resolves validated accessibility settings through a pure helper and per-session snapshots, preserving independent overrides and copied tag arrays. Case sessions also expose explicit scanAccessibility calls using resolved enable/tag settings and returning raw axe observations or preserved execution errors. The build and all 99 tests passed locally on Windows; these mocked checks do not establish successful real-browser scans. Tests mock Playwright; dev-container, real-browser, and current CI verification of the `assertValue` slice remain outstanding. Axe scanning and result generation remain future work. The remaining app and reporter workspaces remain scaffolds with notes about their planned source entries and checks:

- `apps/cli/` - command-line app workspace.
- `apps/web/` - Vue editor app workspace.
- `packages/` - reusable workspaces for runner core, plan schema, plan engine, result model, and provisionally reporters.

The root `package.json` declares the npm workspaces, and the root `package-lock.json` records their dependency tree. API and desktop apps remain later possibilities.

## Other proposed folders

These paths are described in `structure.md` but have not been created as part of the initial workspace scaffold:

- `examples/` - sample test plans that demonstrate how Stagehand plans are written and used.
- `docs/` - product and technical documentation for users and contributors.
- `website/` - the public project website, if the project needs one.
- `tests/` - broader tests that cover behaviour across packages or applications.
- `tools/` - repository maintenance and development utilities.

At the repository root, the proposal also calls for project guidance (`README.md`, `CONTRIBUTING.md`, `SECURITY.md`, and `AGENTS.md`) and shared TypeScript configuration. Those files describe or configure the repository as a whole rather than belonging to one application package.

Treat the proposed layout as a guide for decisions, not evidence that every component has been built. The `structure.md` file says so too; a tidy drawing still doesn't make the road appear.
