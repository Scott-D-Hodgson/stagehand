# ATR-002 — Load and validate a test plan

**Epic:** E01  
**Status:** Proposed  
**Priority:** Must  
**Release:** MVP

## User story

As a test author, I want the runner to load and validate a JSON plan before execution so that malformed plans fail early and clearly.

## Description

Support loading from a file for CLI execution and accepting an already-parsed plan through the reusable API.

## Acceptance criteria

### AC-1 — Read plan

The CLI can read a plan from a specified file path and resolve referenced case JSON files. References are portable relative paths based on the plan file's directory; absolute paths, backslashes, and references whose canonical target leaves that directory are rejected. Match paths case-sensitively on all platforms. Normalize `.` segments and repeated `/` before matching; allow `..` only when canonical resolution remains inside the canonical plan directory. Compare duplicate references after normalization. Follow symlinks, junctions, and other filesystem links only when their canonical target remains inside the canonical plan directory. Each case file represents one executable case; a case file may also define a named data set that is promoted into the plan's data-set collection. Case IDs are unique within a plan.

### AC-2 — Invalid JSON

Malformed JSON produces a clear error and nonzero CLI exit code.

### AC-3 — Schema validation precedes execution

The plan is fully validated before a browser is launched.

### AC-4 — File errors are actionable

Unreadable or missing files produce an actionable error without a misleading test-failure report.

### AC-5 — Validate referenced case files before execution
Every referenced case file is resolved and validated before browser startup. Missing, unreadable, invalid, or unsupported case files identify the reference and provide an actionable error. References, including those traversing filesystem links, that resolve outside the canonical plan directory are rejected. A plan with a missing or duplicate normalized reference, an ambiguous imported-file match, or a duplicate case ID is invalid and cannot proceed to execution. First, shared `plan-schema` logic normalizes references and matches them against supplied relative file paths, returning the matched paths and any match issues. The normalized path is only a logical matching key. Node-side loading resolves the original plan reference, checks that its canonical target remains inside the canonical plan directory, and reads the target it checked; it does not rely on the lexically normalized match key for filesystem safety. The editor preserves relative paths through folder import and reads/parses only matched files. Both flows keep each parsed case associated with its matcher result and pass cases to `validatePlanBundle` in plan-reference order, so case validation issues point back to the correct reference. Unreferenced files in an imported folder do not affect the plan's validity and do not need to be parsed. An editor may save an invalid plan as a draft, but must not present it as valid until every reference resolves, every referenced case validates, and the case IDs are unique.
