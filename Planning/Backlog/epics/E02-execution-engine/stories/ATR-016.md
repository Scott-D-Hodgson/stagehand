# ATR-016 - Resolve nested variables and runtime values

**Epic:** E02
**Status:** Proposed
**Priority:** Must
**Release:** MVP

## User story

As a test author, I want predictable fixed variables, locale variants, and per-case data selection so that I can reuse a plan without duplicating steps.

## Description

Support plan-, case-, and step-level definitions with scalar defaults and optional locale variants. Values are fixed execution inputs. These are accepted future contracts; current schemas and runner execution do not implement M5 resolution.

## Acceptance criteria

### AC-1 - Nested scope lookup

Step definitions override case definitions, and case definitions override plan definitions. A winning definition replaces the entire inherited definition, including its locale map. Then select its locale/default value; do not merge inherited variants.

### AC-2 - CLI overrides at matching scope

CLI values override JSON at the targeted plan/case scope; normal step-over-case-over-plan shadowing remains. CLI flag syntax and exact data-set/CLI precedence examples still need detailed design.

### AC-3 - Shared-step variable context

Shared groups use the calling case context, including selected named data. They have no separate parameters/private defaults and cannot call another shared group.

### AC-4 - Named data sets

Cases may contribute named sets to the plan collection. A runtime selection targets a case and replaces its default set selection; if absent, use the case default. Selected definitions override same-named case-default definitions. Unknown selected names and duplicate set names fail before browser startup; do not silently fall back on an unknown name. Run-wide selection is deferred.

### AC-5 - Case isolation

Each case has its own fixed resolved inputs. Overrides and selected data cannot mutate another case. Page capture and reassignment are deferred beyond MVP.

### AC-6 - Unknown and missing values

Validate structure throughout the loaded plan. Reject missing effective references and required values before browser startup with actionable diagnostics. Resolve environment values only for effective scope/data-set/locale inputs; unselected and overridden environment references need not exist. A present empty environment value is supplied, not missing.

### AC-7 - No arbitrary execution

References do not permit arbitrary JavaScript, interpolation, reference chains, or list iteration. Ordinary strings, including "${email}", remain literal.

### AC-8 - Scalar definitions and references

Each definition has a required default and optional locale variants. Values are text, numbers, booleans, or protected {"env":"NAME"} references; environment references resolve to text. All variants have the same resolved scalar type. Metadata/reference objects do not permit arbitrary object-valued variables. Use whole-field {"var":"name"} references in action inputs and assertion expected values; locator and browser/run-setting references are deferred.

### AC-9 - Name matching

Variable, data-set, and shared-group names are case-sensitive. Locale tags have separate matching rules.

### AC-10 - Field conversion

Convert numbers/booleans to text for text fields; preserve types elsewhere and validate the consuming field. Conversion occurs after scope and locale selection and does not allow mixed-type variants.

## Implementation approach

M5 keeps the existing v1 contracts while the milestone is in progress. The variable-schema foundation is implemented; continue with small, focused PRs for references, resolution, data sets, shared steps, and protected values. Protected evidence and the current raw-history API gap are specified in [ATR-017](ATR-017.md); no current secret-safety guarantee is implied.

## Synthetic design example

This illustrates the accepted direction only. It is a partial future case, not a document accepted by current schemas or an executed test.

```json
{
  "variables": {
    "email": { "default": "tester@example.invalid", "locales": { "fr-CA": "testeur@example.invalid" } },
    "attempts": { "default": 3 },
    "enabled": { "default": true },
    "password": { "default": { "env": "TEST_PASSWORD" } }
  },
  "steps": [
    {
      "action": "fill",
      "locator": { "css": "#email" },
      "value": { "var": "email" }
    },
    {
      "action": "assertValue",
      "locator": { "css": "#attempts" },
      "expected": { "default": { "var": "attempts" } }
    }
  ]
}
```

The email reference supplies the literal text input; attempts resolves to text "3" for the assertion read. The numeric definition itself remains a number. The protected environment reference stores a name only. A missing effective email reference, unavailable required effective TEST_PASSWORD, unknown selected data set, or duplicate data-set name must fail before browser startup. Unselected or overridden environment references are not resolved. A string such as "${email}" remains ordinary literal text; it is not interpolation or a variable reference.
