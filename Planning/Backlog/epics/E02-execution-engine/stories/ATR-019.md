# ATR-019 — Run axe accessibility scans after each step

**Epic:** E02  
**Status:** Proposed  
**Priority:** Must  
**Release:** MVP

## User story

As a test operator, I want optional axe scans after each completed step so that accessibility issues are detected throughout functional end-to-end runs.

## Description

When enabled for a plan or case, run an axe scan after every completed step. Keep findings attached to their case and group them by URL and violation description within that case; within each group, append only problematic markup not already seen. Report findings separately from functional assertions.

## Acceptance criteria

### AC-1 — Explicit setting

Plan configuration controls whether scanning is enabled by default; case configuration may override it.

Run-level scan configuration also offers an optional rule-tag list. With selected tags, assess rules matching any of those tags. At plan scope, omitted or empty tags use axe's normal defaults without tag restriction. Cases inherit when tags are omitted; a non-empty case list replaces the plan list, and `[]` clears the filter. This option controls the assessment itself, rather than filtering findings after a full scan. Retained finding `tags` remain the rule's metadata and are distinct from this configuration. Plan/case schemas now validate `accessibility.tags` as unique exact tag strings against the pinned axe-core 4.14.0 catalogue and reject unknown tags without modifying input. Runner-core now resolves validated plan/case accessibility settings and exposes per-session snapshots. Direct case-session scans now apply resolved filters before analysis; automatic after-step cadence and finding collection remain pending; exact CLI flag names belong to later CLI implementation.

### AC-2 — Scan each step

When enabled, scans run after every completed step.

### AC-3 — Findings and de-duplication

Findings include URL, rule ID, impact, description, and affected-node details where available. For the same URL and violation description within one case, repeated markup is ignored and newly observed markup is added to the existing finding. Extend the result-model v1 schema and types to represent the URL and affected-node details.

Retain rule `tags` on the finding. For each affected node, retain `html`, structured `target`, available `failureSummary` and `impact`, `xpath` when available, and `relatedNodes`. Related-node information comes from axe's individual checks and includes markup, structured target, and optional XPath. Preserve frame/shadow-DOM selector structure. The accepted selection is recorded under [TE-010](../../../technical-enablers/te-010-axe-integration.md#accepted-retained-fields); the result-model extension now represents `affectedNodes` and flat `relatedNodes`, with exact duplicate related objects rejected. The pure runner-core mapper now flattens check evidence and deduplicates exact related tuples. Mapping integration and per-case collection/deduplication remain unimplemented scanner work.

### AC-4 — Independent outcome

Accessibility findings are recorded separately from soft assertion failures and functional assertions.

### AC-5 — Failure policy

Violations do not fail a case by default. Plan configuration can define the default policy and case configuration can override whether findings fail that case. Record the effective `enabled` and `failOnViolation` settings and scan-tag scope in the case's effective result settings. Preserve the distinction between this input scope and rule `tags` on individual findings; the result schema now requires `effectiveSettings.accessibility` with `enabled`, `failOnViolation`, and resolved `tags`, including when findings are empty. An axe execution error is distinct from a detected violation and follows the runner error policy.

### AC-6 — Report integration

Supported reports include accessibility findings and preserve their distinct classification.
