# ATR-020 — Define the versioned result contract

**Epic:** E03  
**Status:** Proposed  
**Priority:** Must  
**Release:** MVP

## User story

As an integration developer, I want a stable result contract so that reports and integrations can consume outcomes consistently.

## Description

Define overall run, case/test, step, assertion, accessibility, diagnostics, timing, cancellation, and artifact structures, including duration and screenshot references. A versioned JSON Schema in the result-model package is the normative validation contract for emitted result JSON.

The MVP produces one JSON result per run, with a run-level summary and one record per case. Each case record includes its stable ID/name, outcome, duration, failure/error detail, and effective non-secret configuration. JSON retains step/assertion diagnostics and accessibility findings. Artifact references are supported by the result contract when artifact capture is added later. JSON is the sole MVP output format.

## Acceptance criteria

### AC-1 — Versioned result

Results declare a schema/version.

### AC-2 — Distinct outcomes

Functional status, soft assertion failures, accessibility findings, and runner errors can be distinguished.

### AC-3 — Traceability

Results identify each case by its stable case ID and each step by its zero-based index within that case. The result contract does not include a separate step ID; plan authors do not supply one. Results also retain timing. Loop context is deferred with loop execution beyond MVP.

### AC-4 — Safe content

Secrets are excluded or redacted.

### AC-5 — Compatibility

Schema evolution and compatibility policy are documented.

### AC-6 — Run and case fields

The run summary includes overall outcome, start/end timing and elapsed duration, and case outcome counts. Each case includes stable identity, outcome, elapsed duration, and relevant failure/error information. Use `passed` (all required success conditions were met), `failed` (one or more configured test conditions were not met, including functional assertions or accessibility findings when configured to fail the case), `cancelled` (execution was interrupted by cancellation), and `error` (the runner could not execute or complete the case due to an operational error). Preserve the failure source in diagnostics so consumers can distinguish functional assertion failures from configured accessibility failures. Do not add `skipped` to the MVP contract unless a feature that deliberately omits cases is added; case selection is currently Later. Document run-level aggregation rules.

### AC-7 — Artifacts and detailed JSON

JSON preserves step/assertion diagnostics, accessibility findings, effective non-secret configuration, and artifact references, including failure screenshots where captured.

### AC-8 — Stable identity and timing representation

Results identify the logical source plan by its stable plan identifier and plan schema version, and include a version-identified content fingerprint of the plan and referenced case contents used for the run to identify the exact source revision. Identify cases using stable identifiers rather than machine-specific file paths. Case IDs are unique within a plan. Timestamps are RFC 3339 UTC strings, and elapsed durations are integer milliseconds. Use `sha256-v1`: hash the raw bytes of the plan followed by each referenced case in plan order. Prefix each record's label/path bytes and content bytes with their unsigned 64-bit big-endian byte lengths. The plan record uses the fixed label `plan`; each case record uses its normalized plan-relative path with `/` separators. Encode the resulting SHA-256 digest as lowercase hexadecimal. Execution policy defines how durations are measured.

### AC-9 — Result schema validation

The emitted JSON validates against the versioned result JSON Schema. The result-model package's public contract and any TypeScript representation remain aligned with that schema, with fixtures covering valid and invalid results.
