# Backlog guidance

Treat this as the initial requirements draft, not a committed product contract. Follow `README.md` for status and priority labels.

- Keep story and technical-enabler identifiers stable; never reuse an ID.
- Write acceptance criteria as observable outcomes that can be verified. Keep verification notes separate from acceptance criteria.
- Link dependencies by stable IDs where possible. Preserve links to epics, roadmap phases, and decisions when moving items.
- Label unresolved behaviour as open rather than filling gaps with invented certainty. Proposed choices should be identified as proposals.
- Keep plans, examples, and fixtures synthetic. Never include credentials, customer data, or real secrets.
- Treat the JSON plan and result formats as versioned public interfaces. Changes need deliberate compatibility notes and a recorded decision where appropriate.
- Backlog statuses and priorities are planning aids, not delivery commitments. Update summaries and indexes when an item changes state or location.
