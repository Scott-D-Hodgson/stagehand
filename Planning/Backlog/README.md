# Stagehand — Backlog

> **Living document:** All material in `Planning/` is generated by AI through discussions and direction from the developer; it is not written by hand. It provides structure, guidance, and context for ongoing development, and will be reviewed and updated periodically as Stagehand evolves.

This directory contains the initial, version-controlled product backlog for Stagehand.

## Structure

- `product-vision.md` — problem, goals, principles, and scope.
- [`../Roadmap/`](../Roadmap/) — suggested delivery phases; not a commitment.
- `release-plan.md` — proposed MVP boundaries.
- `epics/` — epics and individual user stories with acceptance criteria.
- `example-journeys.md` — concise synthetic journeys showing how planned capabilities fit together.
- `technical-enablers/` — foundational engineering work.
- `cross-cutting/` — requirements that span multiple epics.
- `decisions/` — architecture decision records (ADRs).
- `templates/` — reusable templates for future backlog items.

## Status and priority conventions

**Status:** `Proposed`, `Ready`, `In Progress`, `Done`, `Deferred`, `Superseded`.

**Priority:** `Must`, `Should`, `Could`, `Later`.

These are initial planning labels. They are not estimates or commitments.

## Backlog conventions

1. Story IDs are stable and must not be reused.
2. Acceptance criteria describe observable outcomes and should be testable.
3. Verification notes suggest evidence; they do not replace acceptance criteria.
4. Requirements and architectural decisions change through reviewed Git commits or pull requests.
5. A story's dependencies should refer to stable IDs where possible.
6. User plans and secrets do not belong in this backlog. Example plans must use synthetic data.
7. The JSON plan schema and result contract are versioned Stagehand interfaces. Changes should be deliberate and documented.

## Scope note

This is an initial draft generated from Stagehand planning discussions. Review priorities, story boundaries, dependencies, and exact behaviour before treating items as committed scope. The developer has settled the baseline action vocabulary, variable scopes, loop bound, accessibility scan cadence/default outcome, editor-first sequence, and initial platform boundary; implementation details and reporting/status mappings remain open where noted.
